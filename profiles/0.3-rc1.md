# RPP 0.3 RC1 wire profile

This candidate supplies the concrete encoding for §§6–15 of the [specification](../SPECIFICATION.md). Every RC1 peer implements the baseline below. A peer with a different draft layout must explicitly negotiate a future profile or republish its manifest. The version on the wire is unsigned integer **3**, selected by the Link request path `/rpp/3`. Never infer a compatible version from similar fields.

## Encoding and bounds

Encode exactly one RFC 8949 §4.2.1 deterministic CBOR item. Maps use unsigned integer keys in increasing order. Use shortest integer and length encodings, definite sizes, valid UTF-8, unsigned 64-bit integers, byte strings, arrays and maps. Reject negative integers, floats, tags, simple values, duplicates, extra items and unassigned core keys. Null occurs only in the outer result. No implicit defaults for required fields. Optional fields are omitted. No Unicode or path normalization during hashing.

A Destination is 16 bytes, a digest 32, an Ed25519 signature 64. IDs, digests and signatures use CBOR byte strings. Time is UTC Unix seconds. Bounds are inclusive. Check declared lengths against remaining bytes and limits before allocation, use checked arithmetic for all ranges and sums, and apply ingress quotas before buffering or expanding ranges.

| Item | Profile maximum |
|---|---:|
| Control including response wrapper / signed manifest | 4 KiB / 4 MiB |
| Nesting / UTF-8 bytes per text item | 12 / 1,024 |
| Files / chunks per package | 4,096 / 65,536 |
| Logical package bytes / single chunk | 4 GiB / 1 MiB |
| Logical bundle bytes / outstanding Resources per identified Link | 4 MiB / 8 |
| Selection entries or explicit indexes per control | 256 |
| Capability bytes / extension entries per map | 256 / 16 |

Peers may impose smaller admission, link, disk or airtime limits. Lower limits cause a smaller request, deferral or explicit rejection. They never change signed chunk boundaries.

## Manifest and publication

| Keys | Value and rule |
|---|---|
| 0, 1 | Type 0 (Manifest), version 3. |
| 2, 4, 7 | Package digest, publisher’s `rpp.receive` Destination derived from the Package owner Identity, owner signature. |
| 8, 9 | Package and Manifest RDO Destinations. Resolve both using RDO shared-Identity owner binding v1 and require the same owner. Derive and compare key 4 from that verified Identity. |
| 20, 24 | Total logical bytes, chunk count. |
| 31, 32 | Nonempty array of file descriptors, complete array of chunk descriptors. Both required. |
| 6, 12, 14, 15 | Optional creation time, exclusive expiry, nonempty array of distinct predecessor package digests, unsigned publisher sequence. If both times exist, expiry must follow creation. |
| 25, 33, 34, 35 | Optional content type, display name, content version and application profile, all text. |
| 10, 11 | Optional extensions map and critical ID array, as below. |

Other draft manifest fields (26–29 and 36) are reserved in RC1. The baseline carries logical bytes without application compression or encryption. The RNS link still provides its normal protection. An extension affecting interpretation must be critical. **Extension keys 10 and 11** also apply to all seven control maps. Key 10 maps unsigned extension IDs to allowed CBOR values. Key 11 lists distinct, increasing IDs present in key 10. No extension IDs are assigned by RC1. Reject unknown critical IDs before acting. Preserve unknown noncritical entries in every digest, signature and retransmission of the signed artifact.

Each file is a map with required keys 20 (logical size), 40 (relative UTF-8 path), 41 (file SHA-256), 43 ([first chunk index, count]) and 46 (File Destination). Key 25 optionally supplies media type text. Key 42, if present, is [byte offset, byte length] in the logical package stream and must match the derived interval. Entries are in strictly increasing UTF-8 path byte order, paths and File Destinations unique. For portable extraction require nonempty slash-separated components, no empty, dot or dot-dot components, backslash, colon, NUL or ASCII control characters. Reject filesystem collisions and unsafe links during local promotion.

Each chunk requires keys 23 (zero-based position), 20 (positive logical length), 21 (SHA-256). Optional 22, 44, 45 must equal digest, cumulative offset and length respectively. Files partition the chunk array in order, with no gaps, overlaps or cross-file chunks. The first range starts at 0, including for empty files. Each next range begins at the previous end. File lengths equal the sum of their chunk lengths. An empty file has zero chunks and SHA-256 of zero bytes. An all-empty package has zero total size and no chunks. Repeated chunk digests at different positions are valid.

1. Allocate Package, Manifest and File Destinations before hashing. Encode the complete manifest with keys 2 and 7 absent. SHA-256 of those bytes is key 2.
2. Insert key 2. Ed25519-sign the deterministic bytes with key 7 absent, using the resolved Package owner's signing key. Insert the signature at key 7.
3. SHA-256 of the exact signed bytes is the external manifest hash H. Verify all three steps and the advertised references. A file digest covers its concatenated logical bytes. A chunk digest covers only that chunk. Equal file bytes can occur under different owners and package IDs.

Publish RDO revisions through owner authority. For the M2 Package and Manifest types, the revision body is {0: package Destination, 1: manifest Destination, 2: package digest, 3: H}. Both records are immutable. Reject PROPOSE on either type after genesis. The File body uses the same snapshot reference plus key 4 (file digest) and key 5 (path). The File owner alone can issue a successor. An authenticated authorized RDO READ of a File resolves a package reference. READ of Package or Manifest returns its signed publication reference. Verify the owner and compare the reference with the signed manifest before first acceptance. File entries are snapshots of bytes; a third-party File reference cannot update that File. Create fresh Package and Manifest Destinations for an update, optionally name the predecessor and retain the old version. Store the publication reference with the verified manifest for offline use.

## Private Link requests and results

Offer targets the selected peer's SINGLE `rpp.receive` Destination. Derive it with its public RNS Identity, app `rpp`, aspect `receive`. All pulls, acceptance and receipts target the canonical Package Destination. Resolve the Package by its RDO hash and identify the initiating peer on the Link. For Offer verify the identified sender equals the independently resolved Package owner and the recipient equals this inbox. For pulls derive the inbox from the identified requester and compare it with key 5. Check local owner policy at each request and again before sending bytes. Optional capabilities are opaque, owner-issued grants verified or looked up against recipient, operation, package, manifest hash and expiry. Deny on missing/expired/revoked scope. A cached artifact or hash grants no pull permission.

For one Package, peers SHOULD reuse a healthy, identified Link for pulls, plans, accepts, Resources and receipts while endpoint, version, authority and limits remain valid. Keep bounded per-owner session counts, configurable idle timeouts and fair scheduling across active transfers. Recheck authorization on each operation. A Link has a fixed Destination. An Offer on the recipient inbox and a pull on the Package are separate endpoint roles. Open a new Link when the required endpoint changes. The [multi-object service binding proposal](https://github.com/FreeTAKTeam/rpp-spec/issues/3) would require explicit negotiation before a service could dispatch to multiple Package Destinations.

Use native Link request path `/rpp/3` with exact CBOR bytes as request data. The response is encoded CBOR bytes for the RDO v1 result array [1, id, status, null, value]. Status values 0 through 6 are APPLIED, REJECTED, PENDING, STALE, NOT_AUTHORIZED, NOT_FOUND, ERROR. On success value is null or a bstr containing the specified reply command. Return NOT_AUTHORIZED for unauthorized or revoked access, REJECTED for an expired request, invalid selection, unsupported critical extension or unsatisfiable size, and ERROR for local failure. On refusal use null and disclose no private inventory. Represent a denial as an outer status for a decodable request with a supported header. Unsupported versions never fall back to a prior draft. Drop unparseable or unidentified traffic. Requests and positive replies use the same map header:

| Key | Meaning |
|---:|---|
| 0, 1 | Command number, version 3. |
| 2, 3 | Package ID, H. |
| 4, 5 | Package Destination, selected recipient inbox Destination. |
| 6, 12 | Issue time and exclusive expiry. Require issue time ≤ now < expiry and 1–300 seconds lifetime. |
| 13 | Fresh random 16-byte logical request ID. Embedded reply echoes the ID, times and keys 2–5 of its request. |
| 10, 11 | Optional extensions and critical IDs. |

All header fields except 10 and 11 are required. The following table exhausts the other allowed fields. Numbers in parentheses are wire assignments.

| Command | Additional map entries | Exchange |
|---|---|---|
| Offer (1) | Required 9 Manifest Destination. Optional 16 capability. | Owner → inbox. Success returns OfferAck. Check current policy before disclosure. |
| OfferAck (2) | Required 17 decision: rejected 0, accepted 1, already_have 2, defer 3, request_manifest 4, request_plan 5. | Inbox → owner in Offer result. A decision signals intent. In RC1 the receiver follows with a separate pull. |
| ManifestRequest (3) | Required 18 maximum accepted signed-manifest bytes (1–4 MiB). Optional 16 capability. | Receiver → owner on cache miss. APPLIED reserves one manifest Resource. |
| ResourcePlan (4) | Required 19 ordered array of distinct chunk indexes, 20 exact payload length, 21 bundle SHA-256, 22 plan ID (16 bytes). | Owner → receiver in MissingChunks result. Positive plan selects ≥1 outstanding requested index. Plan ID equals that MissingChunks request ID. |
| ResourceAccept (5) | Required 22 plan ID, 17 decision: accept 0, reject 1, defer 2. Optional 16 capability. | Receiver → owner on the same Link. Only accept allows this exact bundle to be sent. A smaller plan requires a fresh pull. |
| TransferReceipt (6) | Required 17 status: failed 0, partial 1, complete 2, complete_verified 3, rejected_after_verification 4. Required 24 verified chunk count, 23 missing selection. Optional 16 capability. | Receiver → owner. APPLIED records the report. Only status 3 confirms verified completion. |
| MissingChunks (7) | Required 23 selection, 18 maximum logical bundle bytes (1–4 MiB), 30 window (1–8). Optional 16 capability. | Receiver → owner. Returns one ResourcePlan or, for an empty selection, APPLIED/null. |

A selection is a sorted array of unsigned indexes or [first,last] inclusive ranges. Require in-bounds, nonoverlapping entries with first ≤ last. Validate before expansion. Receipt selection may describe a bounded subset of remaining gaps. For status 3 require verified count equal to manifest chunk count and empty selection. A plan may cover part of a request. Release the unused selection after processing the plan and request the rest separately. Parallel pulls must select disjoint outstanding indexes. Take the minimum of requested window, sender/receiver policy and remaining capacity on the Link. Refuse an indivisible chunk that exceeds the negotiated size. Drop unaccepted plans on expiry. On Link close, policy revocation, package/grant expiry or quota exhaustion, suspend or cancel the affected work. Request expiry limits admission. An admitted Resource may continue while authorized and making progress under a bounded local idle timeout.

## Resource association, replay and completion

Transfer the exact signed manifest or concatenated chunks in plan order as one native RNS Resource per accepted unit. RNS Resource metadata is **one binary value of 16 bytes**, the ManifestRequest ID for a manifest or the plan ID for a bundle (the native RNS metadata codec wraps that value). No inline chunk headers. Disable RNS automatic compression in this baseline when sending. Reserve capacity before issuing ManifestRequest or ResourceAccept. Bound incoming advertisements, buffered bytes and concurrent assemblies before metadata becomes available. Quarantine until APPLIED, the identified Link, metadata ID, expected size or manifest cap, and H/plan match. Charge native metadata/framing overhead separately from the logical payload limit. Refuse unsolicited or over-budget Resources even if metadata arrives late. Match only within the current Link, reject an ambiguous metadata ID, and never reuse a request or plan ID for a distinct reservation on that Link.

Bind replay records to authenticated peer, Package, recipient and request ID through expiry. Compare exact request bytes; identical retries return the recorded result without another allocation, send or promotion. Conflicting reuse is REJECTED. Recheck current authority before returning cached private results. Preserve replay state across restart or refuse outstanding requests through their expiry. Plans are link-local, may be accepted only once, and expire no later than their originating request. Reject a new accept for a consumed plan even when it carries a fresh request ID. Persist verified content separately. On resource loss or a new Link, use fresh IDs, check policy and recompute gaps from verified storage. A manifest is fetched again only on cache miss or failed verification. For identical repeated resource bytes after acceptance acknowledge locally just once; discard a conflicting duplicate, preserve verified bytes and record a failure.

Verify bundle length, bundle SHA-256, and each signed chunk length and digest before marking its index present. Stage bytes privately. Verify every file digest and the signed manifest and publication reference, check authorization/expiry and atomically promote the assembled version before sending complete_verified. A transport callback, offer acknowledgment or count of sent chunks cannot produce that receipt. A partial failure keeps verified data available to resume. A receipt describes the authenticated recipient's assertion and does not independently prove remote storage.

## Fabric and downstream acceptance

Fabric can place the independent library under `crates/libs/rpp-core`. Its codec, digests, inventory, replay and receipt rules accept bytes, verified RDO owner bindings, a clock and caller policy. Its transfer engine needs bounded storage and public RNS Link/Resource adapters. The conformance runner must execute with no daemon, RCH, REM or LXMF message dependency. RCH and REM retain catalog, mission/team authorization, scheduling, UI and storage policy.

| Gate | Entry and required evidence |
|---|---|
| Wire review | Two independent encoders reproduce the [fixtures](../vectors/rc1.json), all command bytes, signatures and digests. Exercise negative cases, empty files, updates, repeated content and 101-chunk restart. |
| RDO and RNS, in parallel | [RDO #1](https://github.com/FreeTAKTeam/ReticulumDistributedObject/issues/1) verifies signed hash-only lookup and owner operations between Python and Rust. [Fabric #766](https://github.com/FreeTAKTeam/LXMF-rs/issues/766) verifies bounded disk streaming, metadata preservation, multi-Resource association, cancellation, loss and mixed-peer operation. Reuse closed Resource issues #514, #552–554 and #610 as regression evidence. |
| Independent engine | [Fabric #767](https://github.com/FreeTAKTeam/LXMF-rs/issues/767) consumes the three preceding contracts. Require standalone transfer, restart, verified receipt and isolation under concurrent peers. |
| Applications | [RCH #354](https://github.com/FreeTAKTeam/Reticulum-Community-Hub/issues/354) and [REM #356](https://github.com/FreeTAKTeam/reticulum_mobile_emergency_management/issues/356) can align catalog/local storage in parallel. [RCH #355](https://github.com/FreeTAKTeam/Reticulum-Community-Hub/issues/355) needs catalog and engine. [REM #357](https://github.com/FreeTAKTeam/reticulum_mobile_emergency_management/issues/357) adds hub discovery after catalog, engine, local library and serving. [REM #358](https://github.com/FreeTAKTeam/reticulum_mobile_emergency_management/issues/358) needs engine and local library for direct peer transfer. Run the joint RCH↔REM and two-device matrix after serving and both REM transfer paths exist. |

The JSON fixtures pair each diagnostic `value` with exact `cbor_hex`. Decimal object keys represent CBOR uints and strings of the form `h'00ff'` represent bytes. Other strings are text. Each package case stands alone. All private-key inputs are public test patterns. `resume_publication` supplies the three signed RDO publication records for the 101-chunk case. Run it once on a cache miss and again with only indexes 17 and 63 missing. The latter run transfers two logical bytes, zero manifest bytes. With separate accepted plans an interruption after index 17 leaves only 63. The negative cases use the resume scenario unless the fixture supplies a different artifact or precondition. For false completion, check the recipient's receipt creation against its actual inventory.

For Link reuse qualification, transfer 100 chunks in ten accepted bundles on one authorized Package Link, then interrupt and reconnect. Record path/Link establishment and stamp costs separately from payload throughput. Require one initial Link, no new Link establishment per bundle, correct resource correlation, and a cached-manifest resume after reconnect. Test strict stamp admission against the RNS portion of [Fabric #768](https://github.com/FreeTAKTeam/LXMF-rs/issues/768).

RC1 is a design target. A published interoperability claim requires the RDO and RNS network gates. Product and radio claims additionally require their corresponding device evidence.
